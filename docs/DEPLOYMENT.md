# Deployment: Render + Supabase

One container on Render runs the console, the JSON API and all five agents (in-process). Supabase Postgres holds
everything that must outlive a restart. Nothing else is needed: no second service, no queue, no object store.

```
 phones / laptops / judges ──https──▶ Render web service (Dockerfile)
                                       ├─ console (/), review queue (/ui/review), admin (/admin), phone stations
                                       ├─ JSON API (/workflows, /evidence, /health, /whoami, /docs)
                                       ├─ orchestrator ──▶ receiving · prep · pack · returns · recovery (in-process)
                                       └─ psycopg pool ──▶ Supabase Postgres, schema pod12
                                                            workflows · evidence · files · audit · access_codes · faults
```

## What lives where

| State | Table | Notes |
|---|---|---|
| Workflow State | `pod12.workflows` | full JSON (`body`) plus `org_id`, `status`, `outcome` columns to query |
| Evidence records | `pod12.evidence` | write-once: a second write must carry the same `content_hash`, else it is refused |
| Capture photos, Returns reference photos and cards, Pack reuse ledger | `pod12.files` | the agents still read files: every change is written here, and the files are put back on disk when the container starts (with their original modification times) |
| Who did what | `pod12.audit` | every sign-in, failed sign-in, change (POST) and admin action |
| Access codes | `pod12.access_codes` | SHA-256 only, each for one org or all, revocable |
| Fault switches | `pod12.faults` | agents an admin has switched off to show failure handling |

The tables are in their own schema, not `public`, so Supabase's auto-generated REST API does not publish them.

## Access

| Who | How | Sees |
|---|---|---|
| Admin | `/login` with `ADMIN_PASSWORD` (generated by Render; Render > pod12-console > Environment) | every org; `/admin`: system state, fault switches, access codes, every workflow, audit log |
| Teammate / judge | `/join` with an 8-digit code the admin issued | only the org of the code (or every org for an all-org code) |
| API client | `Authorization: Bearer <code or admin password>` | same as the code |
| Anyone | `/health` | agent and database status only |

Another org's case, workflow, evidence record or photo answers **404**, exactly as if it did not exist.

## For the judges (try it)

1. Open the deployment URL and sign in at `/join` with the code you were given.
2. Units: pick a unit, add photos (or use the phone camera), run it, open the workflow, follow the final outcome back to
   each record and its photo hashes. `GET /evidence/<record_id>` re-checks a record's `content_hash`.
3. Review queue (`/ui/review`): an UNCERTAIN result waits there; record an override (the original record is kept) or
   resume.
4. Failure test: the admin switches an agent off on `/admin` (down, timeout or contract-breaking output). Run a unit:
   the stage errors and the workflow ends FAILED/INCOMPLETE, never CLEAN. Switch it back on, press Resume.
5. Tenancy test: with a code for `org_demo_bravo`, try `GET /workflows/WF-org_demo_alpha-UNIT-0014`: 404.

```bash
curl -H "Authorization: Bearer <code>" https://<deployment-url>/workflows
curl -H "Authorization: Bearer <code>" -X POST https://<deployment-url>/workflows \
     -H "content-type: application/json" -d '{"org_id":"org_demo_alpha","unit_id":"UNIT-0014"}'
```

## Set it up (once)

1. **Supabase**: New project (region South Asia, Mumbai). Connect > **Session pooler** > copy the connection string,
   put the database password in it. (Not "Direct connection": that host is IPv6-only and Render cannot reach it.)
2. **Render**: New > Blueprint > this repository. It reads `render.yaml`, builds the `Dockerfile`, generates
   `ADMIN_PASSWORD` and `SESSION_SECRET`, and asks for `DATABASE_URL` (step 1) and `GEMINI_API_KEY`.
3. First start creates the tables. Sign in at `/login`, issue codes on `/admin`.

Free Render instances sleep after 15 minutes without visitors (the first visit then takes about a minute) and have
0.1 CPU. For the demo, switch the instance type to Starter (Settings > Instance type) or keep it awake.

## Locally

Nothing changes on a laptop: without `DATABASE_URL` state stays in JSON files under `out/`, and without
`ADMIN_PASSWORD` / `POD_LAN_CODE` the console is open, as before. To test against a real Postgres:

```bash
TEST_DATABASE_URL=postgresql://... pytest tests/integration/test_postgres_store.py
```

It works in a throwaway schema (`pod12_test_<random>`) and drops it afterwards.

## Limits (said plainly)

- One container, one worker: a workflow is read and written whole, so two people pressing Run on the same unit at the
  same moment can race. The phone stations take turns by design (each step waits for the one before it).
- Photos live in Postgres as bytes. Fine for a demo's few hundred photos; a production system would use object storage.
- The content hash shows a record was not changed by accident; it is not a signature against someone with database
  access (see EVIDENCE-CONTRACT.md).
